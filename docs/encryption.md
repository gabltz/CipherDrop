# Encryption protocol (v1)

This page is the normative specification of CipherDrop protocol version 1. The reference implementation is the Rust crate `cipherdrop-protocol` (`crates/protocol`). Every official client is tested against the shared vectors in `crates/protocol/testdata/vectors.json`.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## Primitives

| Purpose | Algorithm | Parameters |
|---|---|---|
| Content encryption | AES-256-GCM (NIST SP 800-38D) | 256-bit key, 96-bit nonce, 128-bit tag |
| Password hardening (optional) | Argon2id v1.3 (RFC 9106) | memory 19456–262144 KiB, iterations 2–10, parallelism 1–4; output 32 bytes |
| Key combination | HKDF-SHA256 (RFC 5869) | output 32 bytes |
| Randomness | OS CSPRNG (`getrandom`, `crypto.getRandomValues`, `secrets`, `RandomNumberGenerator`) | |
| Binary-to-text | base64url without padding (RFC 4648 §5), canonical | |

No custom primitives are used. Compression is never applied.

## Key and nonce generation

1. The sender generates a fresh **share key** `K`: 32 bytes from a CSPRNG. Every share has its own key. A key MUST NOT be reused for another share.
2. For each encryption, the sender generates a fresh 12-byte **nonce** from a CSPRNG. Because each key encrypts exactly one message, the (key, nonce) pair is never reused.

## Content-encryption key (CEK)

**Without password:** `CEK = K`.

**With password `P`:**

```text
salt = 16 random bytes
PW   = UTF-8( NFC(P) )                         # Unicode Normalization Form C, then UTF-8
PWK  = Argon2id(password = PW, salt = salt, m = memory_kib, t = iterations,
                p = parallelism, version = 0x13, output length = 32)
CEK  = HKDF-SHA256(salt = salt, IKM = K ‖ PWK, info = "cipherdrop/v1/cek/password", L = 32)
```

The password *supplements* the random key and never replaces it. Decrypting needs both the complete link and the password. Offline guessing of the password is only possible for an attacker who already holds the full link (including `K`) and the ciphertext. Each guess then costs one Argon2id evaluation with the sender's parameters. Empty passwords MUST be rejected.

## Plaintext payload

The plaintext is a UTF-8 JSON object:

```json
{"content":"…","title":"optional title","syntax":"rust"}
```

- `content` (string, required): the secret.
- `title` (string, optional), `syntax` (string ≤ 32 bytes, optional): metadata, encrypted like the content.
- Readers MUST ignore unknown fields.
- Writers SHOULD append ASCII spaces (`0x20`) after the JSON value so the total length is a multiple of 256 bytes. JSON parsers ignore trailing whitespace, and padding hides the exact length of short secrets.

## Associated data (AAD)

The AAD binds the protocol version, the algorithm and every KDF parameter to the ciphertext. It is the ASCII string:

```text
no password:   cipherdrop/v1;alg=AES-256-GCM;kdf=none
with password: cipherdrop/v1;alg=AES-256-GCM;kdf=argon2id;v=19;m=<memory_kib>;t=<iterations>;p=<parallelism>;salt=<salt>
```

Integers are base-10 without sign or leading zeros. `<salt>` is the canonical unpadded base64url encoding of the 16 salt bytes. Any change to these envelope fields, including removing `kdf` (a downgrade), makes authentication fail.

## Encryption

```text
ciphertext ‖ tag = AES-256-GCM-Encrypt(key = CEK, nonce = nonce, plaintext = payload, aad = AAD)
```

The 16-byte tag is appended to the ciphertext (the default output layout of every common AES-GCM API). There is no length prefix and no byte-order concern: all fields are byte strings.

## Envelope (wire format)

```json
{
  "version": 1,
  "algorithm": "AES-256-GCM",
  "nonce": "<base64url, 12 bytes, 16 chars>",
  "ciphertext": "<base64url of ciphertext ‖ 16-byte tag>",
  "kdf": {
    "algorithm": "argon2id",
    "salt": "<base64url, 16 bytes, 22 chars>",
    "memory_kib": 65536,
    "iterations": 3,
    "parallelism": 1
  }
}
```

`kdf` is present if and only if a password is used. Recommended defaults: `memory_kib = 65536`, `iterations = 3`, `parallelism = 1`.

Validation rules (applied by the server on upload and by clients before decrypting):

- `version` MUST be `1`; `algorithm` MUST be `"AES-256-GCM"`; unknown fields MUST be rejected.
- base64url MUST be canonical: no padding, no whitespace, no `+` or `/`, and unused trailing bits zero.
- `nonce` MUST decode to 12 bytes; `ciphertext` to at least 16 bytes; `kdf.salt` to 16 bytes.
- KDF parameters MUST lie within the bounds above. Clients MUST refuse to run Argon2id with out-of-bounds parameters, which protects recipients from memory-exhaustion attacks.

## Share and revocation links

```text
share link:       {public_url}/s/{share_id}#v1.{base64url(K)}
revocation link:  {public_url}/revoke/{share_id}#v1.{revocation_token}
```

- `share_id`: 16 random bytes generated by the server (22 chars). It is an identifier, not a key.
- `K`: 43 characters after `#v1.`.
- The fragment MUST NOT be sent to the server in any request, header, log or error report. Clients send only `share_id`.
- The `v1.` prefix versions the fragment format. Unknown prefixes MUST be rejected.

## Decryption and error handling

1. Parse the link and validate `share_id` and `K`. On failure: *malformed link*. Do not contact the server.
2. `POST /api/v1/shares/{id}/consume`. On `404`: *unavailable*. Never retry automatically.
3. Validate the envelope. On failure: *malformed envelope*.
4. If `kdf` is present, obtain the password and derive the CEK. Keep the envelope in memory, so password retries do not consume another retrieval.
5. Decrypt with the AAD. On authentication failure, report one generic error: *wrong key, wrong password, or modified data*. Implementations MUST NOT reveal which.
6. Parse the payload; on failure: *malformed payload*.

Implementations SHOULD wipe keys, passwords and plaintext buffers after use (best effort; garbage-collected runtimes cannot guarantee erasure).

## Limitations

- **Length leakage.** Ciphertext length reveals plaintext length up to the 256-byte padding granularity.
- **Server-supplied code.** In the browser, the encryption code itself is delivered by the server. See [Security](security.md#trusting-the-web-client).
- **No forward secrecy.** Anyone who obtains the link and a copy of the ciphertext can decrypt it at any time. Deleting the ciphertext from the server is what limits exposure.
- **No sender authentication.** Anyone with creation rights can produce shares; the protocol does not sign content.
